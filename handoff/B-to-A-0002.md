# B-to-A-0002: register-h0.ps1 schedules the wrong date on a dd/MM/yyyy locale

id: B-to-A-0002
from: B
to: A
status: open
opened: pre-jam (2026-11-12 01:10 CET)
deadline: before H0

## What

Check device A's task now: `(Get-ScheduledTask ThirdJam-H0 | Get-ScheduledTaskInfo).NextRunTime`. If it reads 11 December, correct it; then make
`tools/h0/register-h0.ps1` independent of the regional date format and verify the date it prints.

## Why

On device B (`Get-Culture` = en-GB, short date `dd/MM/yyyy`) the script registered `ThirdJam-H0-B` for **2026-12-11 06:00** and still printed
`PASS task ThirdJam-H0-B at 2026-11-12 06:00 local`. It passes `/SD` as `MM/dd/yyyy`; `schtasks` reads `/SD` in the system's regional format, so
`11/12/2026` became 11 December. Both devices belong to the same operator, so A probably has the same setting; if so, A's unattended start will not fire.
The PASS line prints the requested time, not the registered one.

Corrected on B without touching the script:

```powershell
Set-ScheduledTask -TaskName ThirdJam-H0-B -Trigger (New-ScheduledTaskTrigger -Once -At ([datetime]::new(2026,11,12,6,0,0)))
```

Two more defaults of `schtasks /Create` worth changing on a laptop (B changed both): `DisallowStartIfOnBatteries` and `StopIfGoingOnBatteries` are
true, so the task does not start on battery and is stopped if AC drops.

**Added at H4 (B):** this note never reached A before H0 (it was uncommitted on B when Windows Update restarted both machines at about 02:34). Neither
start fired, for the reason `status/A.md` gives: the task needs an interactive logon and nobody was logged on after the restart. The date bug is
still in the script for any later use. Two more things would have saved the night on both machines: pause Windows Update for the jam, and register
the task with `StartWhenAvailable` so a missed start runs at the next logon.
